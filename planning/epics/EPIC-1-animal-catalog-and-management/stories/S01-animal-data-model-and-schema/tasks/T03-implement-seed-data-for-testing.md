## Overview

Create a seed data module that inserts representative animal records into the database for use in integration tests and local development. The seed data covers all animal statuses, multiple species, and realistic Paraguayan shelter context with Spanish descriptions. This task also defines the pytest fixtures that integration tests use to create specific animal records within the rollback-isolated test transactions.

## Why This Matters

Integration tests need predictable, realistic data to verify that API endpoints return correct results. Without a seed strategy, developers create throwaway records inline in each test function, leading to inconsistent naming, missing edge cases (no animal in medical_hold status, no featured animal), and test maintenance burden when schema changes require updating dozens of inline record definitions. Centralizing seed data in one place means all tests draw from a consistent, well-documented set of baseline records.

For local development, seed data provides a realistic starting state that allows developers to browse the catalog, test the admin dashboard, and verify filtering logic without manually inserting records through the API.

## Context

The project uses SQLAlchemy 2.x sessions for all database interaction. Seed data is expressed as Python code that creates SQLAlchemy model instances and adds them to a session — there are no raw SQL INSERT statements anywhere in the test or seed infrastructure. Primary keys are integers generated by PostgreSQL autoincrement, so seed records do not specify explicit id values. The rollback isolation pattern in the test suite (described in EPIC-0/S03) means that each test function starts with a clean snapshot and all records created by fixtures disappear after the test completes without any DELETE statements.

The ten representative animals in the seed set are deliberately diverse: different statuses (available, reserved, adopted, medical_hold), different species (dog, cat, rabbit), different ages, some with microchip numbers and some without, some featured and some not, drawn from different cities in Paraguay (Asunción, Luque, San Lorenzo, Fernando de la Mora, Capiatá). This diversity ensures that filter tests have something to find and something to exclude regardless of which filter combination is being tested.

## Implementation Steps

### Step 1: Create the Seed Module

Create the file tests/seed.py (or alembic/seed.py if the seed data should also be runnable against the development database outside of tests). This module contains a single function named create_seed_animals that accepts a SQLAlchemy Session as its argument and inserts the ten representative animals into the session.

The function should call session.add() for each Animal instance individually rather than session.add_all() with a list, so that each insertion is easy to read and modify independently. After adding all animals, the function calls session.flush() rather than session.commit() when called from test fixtures, so the records get database-assigned primary keys without ending the transaction that the rollback fixture will later undo. When called from a development seed script, the caller is responsible for committing.

### Step 2: Define the Ten Representative Animals

The ten animals provide coverage across all critical dimensions that the catalog and filtering endpoints need to handle. Their descriptions are in Spanish to reflect the shelter's operating language and the likely language of staff entering records.

The first animal is a large male dog named Capitán, available for adoption, estimated at 36 months, from Asunción, described as a mestizo dog with brown fur who gets along well with children and is looking for a home with a yard. He is vaccinated, neutered, and featured on the homepage.

The second animal is a small female cat named Luna, also available, estimated at 24 months, from Luque, described as a calm domestic cat who is good for apartments. She is vaccinated and neutered.

The third animal is a medium male dog named Bruno, in reserved status (an adoption application is pending), estimated at 48 months, from San Lorenzo. He is vaccinated but not yet neutered, has a microchip number recorded, and is described as a friendly mix who loves going for walks.

The fourth animal is a female rabbit named Canela, available, estimated at 12 months, from Asunción, described as a small domestic rabbit suitable for children. She has no vaccination or neutering status recorded because those fields are not applicable in the same way for rabbits.

The fifth animal is a male dog named Rex, in medical_hold status, estimated at 60 months, from Fernando de la Mora, described as being under veterinary treatment for a leg injury and not currently available. He is not featured.

The sixth animal is a female cat named Mia, available, estimated at 18 months, from Capiatá, described as a playful young cat who enjoys company. She is vaccinated.

The seventh animal is a male dog named Toby, adopted status, estimated at 84 months, from Luque, described as an older dog who found his forever home. He serves as the test record for the adopted status, which should not appear in public catalog searches.

The eighth animal is a small female dog named Princesa, available, estimated at 6 months, described as a puppy mix rescued from the street, very friendly, seeking a patient family. She is featured on the homepage and is the youngest record in the seed set.

The ninth animal is a male dog named Sombra, available, estimated at 30 months, from San Lorenzo, described as a black medium-sized dog, calm and obedient. He has a microchip number recorded.

The tenth animal is a female cat named Tigresa, in medical_hold status, estimated at 36 months, from Asunción, described as receiving treatment and not yet available. She provides a second medical_hold record, useful for testing that aggregate counts of animals in this status are correct.

All ten animals are assigned to the same shelter record created by the shelter seed fixture that this module depends on.

### Step 3: Define pytest Fixtures for Individual Animals

In tests/conftest.py, define fixtures that create individual animal records within the rollback-isolated test session. These are the fixtures that integration test functions declare as function arguments when they need a specific animal to exist in the database before their HTTP request is issued.

The primary fixture is named animal and creates a single available dog. It accepts the db_session fixture as a dependency, creates one Animal instance with well-known attributes (name "Test Dog", species dog, status available), calls db_session.add() and db_session.flush() to get the database-assigned id, and returns the Animal instance. The test function receives this instance and can use its id attribute to construct URLs like the GET /animals/{id} path.

A second fixture named unavailable_animal creates an animal with status medical_hold. This fixture exists so tests that verify the public catalog does not expose unavailable animals have a specific record to check against.

A third fixture named featured_animal creates an animal with is_featured set to True. Tests for the homepage featured section use this fixture.

All individual animal fixtures follow the same pattern: create instance, flush to get id, return instance. They never commit. The rollback in the db_session fixture handles cleanup.

### Step 4: Define the NONEXISTENT_ANIMAL_ID Constant

In tests/conftest.py, define a module-level constant NONEXISTENT_ANIMAL_ID with value 999999. This constant is used by integration tests that need to verify 404 responses. Using a named constant prevents the magic number 999999 from appearing in multiple test files and documents the intent clearly. The value 999999 is chosen because integer autoincrement primary keys generated during tests will never reach this value, guaranteeing that no real animal record will ever have this id during a test run.

### Step 5: Create a Development Seed Script

Create a standalone script at scripts/seed_dev.py that imports create_seed_animals and runs it against the development database. This script reads DATABASE_URL from the environment, creates a SQLAlchemy engine and session, calls create_seed_animals(session), and commits the transaction. Running this script after alembic upgrade head gives a developer a fully populated local database in one step.

The script should check whether animals already exist before inserting, to make it idempotent. If the animals table is not empty, the script should print a message saying the database is already seeded and exit without inserting duplicates.

## Common Issues and Solutions

If seed animals are created but their ids are None after flush, verify that the SQLAlchemy session is configured to expire objects after flush. The flush() call writes the INSERT to the database transaction, and PostgreSQL returns the autoincrement id, but SQLAlchemy only loads the id back into the Python object if expire_on_commit is False or if the object is refreshed explicitly with session.refresh(animal). Add session.refresh(animal) after flush() to guarantee the id is populated.

If the seed script inserts duplicate records on repeated runs, the idempotency check is not working. Verify that the check queries for an existing record by a stable unique attribute (such as a combination of name and intake_date) rather than by id, since ids will differ between runs if the database was reset.

If integration tests that depend on the animal fixture receive a 404 from the API, the rollback isolation is working correctly but the animal's id is being used in a URL before the flush returns it. Ensure the fixture calls flush() before returning the animal instance, and that the test function uses animal.id only after the fixture has completed setup.
