# Create Component-Level Tests for Service Classes

## Overview

Component-level tests verify that individual service classes function correctly in isolation with their external dependencies mocked at the boundary. Unlike unit tests that test small utility functions, component tests exercise complete service methods with realistic workflow scenarios, complex validation logic, and boundary interactions with the database, email system, and payment processor. These tests sit at the middle layer of the testing pyramid and provide confidence that individual services work as designed before integration testing verifies their interactions.

In the Refugio Animal Paraguay system, key service components include the AdoptionService handling adoption request lifecycle management with validation and notifications, the DonationService managing donation processing with currency conversion and payment intent creation, the PaymentProcessingService interfacing with Stripe API for actual payment execution, the NotificationService coordinating email delivery with retry logic and audit logging, and the AnimalService managing animal inventory with status transitions and adoption blocking logic. Component tests mock the database through a test database fixture, mock external services like Stripe and email providers at their API boundaries, and exercise complete service workflows from request to response including error conditions and edge cases.

Component testing focuses on service method behavior rather than implementation details, ensuring tests remain stable during internal refactoring. Tests verify that correct database queries are executed (without inspecting exact SQL), that external service calls occur with appropriate parameters, that validation logic rejects invalid inputs with proper error codes, that status transitions follow business rules, and that concurrent requests do not create race conditions or data corruption. The test structure mirrors production service organization with one test class per service class, grouped test methods by service method, and shared fixtures for common setup like valid test animals and adopters.

## Why This Task Matters

Service components form the boundary between application logic and infrastructure. Defects in service components can cause cascading failures: a broken AdoptionService might reject valid adoption requests, blocking legitimate user workflows; a broken DonationService might fail to create payment intents, preventing donation processing entirely; a broken PaymentProcessingService might charge donors twice or fail to charge at all. Component tests catch these defects before they reach integration or production environments.

Component tests also establish the contract that integration tests depend on. Integration tests assume that individual services work correctly and test their interactions; if services contain defects, integration tests cannot distinguish between service bugs and integration issues. By ensuring component tests pass first, integration tests can confidently focus on service interaction patterns, data flowing between services, and end-to-end workflow orchestration.

Component tests provide rapid feedback during development. When a developer modifies a service class, they can run component tests for that service in seconds (rather than spinning up the full integration environment) and get immediate validation that their changes work correctly. This tight feedback loop enables confident refactoring, incremental improvement, and rapid iteration during feature development.

Component tests also serve as executable documentation of service behavior. Reading component test cases shows exactly what inputs a service accepts, what outputs it produces, what exceptions it raises, and how it handles edge cases. This documentation stays synchronized with code changes because tests fail if code and documentation diverge.

## Technical Requirements

Component tests require mocking external dependencies at service boundaries while testing service logic thoroughly. The AdoptionService component tests must mock the database through a test database fixture providing temporary tables and automatic rollback, mock the notification queue to capture email delivery requests without actually sending emails, mock the AnimalService to simulate animal availability checks, and verify that adoption requests correctly validate adopter eligibility through age checks, email validation, and animal status verification. Tests must exercise the complete adoption request submission workflow including validation of all required fields, rejection of underage adopters with appropriate error codes, blocking of adoption requests for unavailable animals, creation of adoption request records in the database, queuing of confirmation emails with correct recipient addresses, and updating of animal status to reserved.

The DonationService component tests must mock the Stripe API to capture payment intent creation calls, mock the database for recording donation records, mock the currency conversion service for EUR to PYG conversion, and verify that donations correctly validate amount values rejecting zero and negative amounts, accept EUR and PYG currencies, convert EUR amounts to PYG using current exchange rates, create Stripe payment intents with correct metadata (donor ID, animal reference if applicable), store donation records with correct status (pending payment), and queue confirmation emails after successful payment intent creation.

The PaymentProcessingService component tests must mock the Stripe API for charge submission and webhook handling, mock the database for payment record updates, mock the notification service for payment notifications, and verify that payment processing correctly handles payment intent status transitions, processes succeeded payment intents by updating donation status to confirmed, handles requires_confirmation status by sending payment confirmation requests to donors, retries failed payments with exponential backoff (5 minutes, 30 minutes, 2 hours), logs all payment state changes to the audit trail, and sends notifications to donors about payment outcomes with clear messaging for failures.

The NotificationService component tests must mock the SMTP email backend to prevent actual email transmission, mock the database for audit logging, mock the retry queue for exponential backoff handling, and verify that notifications correctly compose HTML emails with proper styling, send to correct recipient addresses from the donor or adopter database records, include all required metadata in email headers for tracking and auditing, handle invalid email addresses with error logging, implement retry logic with increasing delays, and prevent duplicate notifications for the same event.

The AnimalService component tests must mock the database for animal inventory management, mock the AdoptionService for adoption blocking checks, and verify that animal status transitions correctly enforce allowed state transitions only, block adoption requests for reserved or adopted animals, update animal timestamps on status changes, prevent concurrent modifications through optimistic locking, and raise appropriate exceptions for invalid transitions with clear error messages.

All component tests must use parametrized fixtures to efficiently test multiple scenarios (valid and invalid inputs, boundary values, error conditions). Tests must use dependency injection to pass mock objects to service constructors rather than mocking through global imports or module-level patches, ensuring test isolation and clear dependency visibility. Tests must verify both success paths and error paths: successful operations return correct response objects with expected values, validation errors raise specific exception types with meaningful error codes, database errors are caught and logged appropriately, and external service failures are retried or failed gracefully. Tests should execute within the test suite in parallel without shared state, completing within 30 seconds total for all component tests combined.

## Implementation Approach

Component tests will be organized in a directory structure under tests/integration/components/ with one Python module per service class (test_adoption_service.py, test_donation_service.py, test_payment_processing_service.py, test_notification_service.py, test_animal_service.py). Each test module will import the service class under test from the production source code, import mock objects and fixtures from conftest.py, and define a test class using pytest's class-based organization with one test method per service method being tested.

The fixture setup will leverage conftest.py fixtures for test database connections and common test data (sample animals, adopters, donors with valid email addresses and ages). Component-specific fixtures will create mocked external dependencies: a mock Stripe client that captures API calls without executing actual charges, a mock SMTP connection that captures email composition, a mock retry queue that tracks exponential backoff scheduling. Each test fixture will be marked with scope=function to ensure complete isolation between tests with fresh mocks and database state for every test.

Tests will use a consistent structure: Arrange phase setting up test data and mocking external dependencies, Act phase calling the service method under test, Assert phase verifying return values, database state changes, and mock calls with specific parameters and call counts. For example, the AdoptionService.submit_adoption_request test will arrange by creating a test animal and adopter, act by calling submit_adoption_request with valid request data, assert that the adoption request record was created in the database with correct status, the animal status was updated to reserved, the confirmation email was queued to the correct recipient, and the returned response contains the adoption request ID.

Service tests will verify error handling by asserting that invalid inputs raise specific exception types with correct error codes: ValidationError for email validation failures, IneligibilityError for age checks, ResourceNotFoundError for missing animals or adopters, ConflictError for attempting to adopt unavailable animals. Tests will use pytest.raises context managers to verify exception type and message content. Tests will also verify logging behavior by capturing log output and asserting that appropriate log messages were recorded for both success and error paths.

Mocking will be implemented through dependency injection at service initialization rather than module-level patches. Each service will accept its dependencies as constructor arguments (database session, email client, external API client), allowing tests to inject mock objects. For example, DonationService will accept a stripe_client parameter that can be a real Stripe client in production or a mock in tests. This design maintains clear dependency visibility and prevents tests from accidentally using production dependencies.

Parametrized tests will use pytest.mark.parametrize to efficiently test multiple scenarios in a single test method. For example, email validation tests will parametrize over valid emails and invalid emails, currency tests will parametrize over positive amounts, zero amounts, and negative amounts, status transition tests will parametrize over allowed and disallowed transitions. This approach reduces code duplication and ensures comprehensive coverage of all input space.

Performance baselines will be established by measuring test execution time for critical service methods. The AdoptionService.submit_adoption_request test should execute in under 100 milliseconds (dominated by database operations), PaymentProcessingService tests should execute in under 50 milliseconds (mostly mocked), and NotificationService tests should execute in under 20 milliseconds. These baselines ensure component tests remain fast enough to run frequently during development.

## Success Criteria

Component tests are successful when the following criteria are met: All service classes have component test coverage with test modules for AdoptionService, DonationService, PaymentProcessingService, NotificationService, and AnimalService, each containing complete test coverage for all public service methods. All test methods pass successfully in the test environment without requiring modifications to service code. All component tests execute within 30 seconds total when run in parallel (--maxfail=5 to fail fast). Code coverage for service classes reaches 90% minimum, ensuring that normal workflows and major error paths are tested. Test organization follows the established structure with tests/integration/components/ directory, one test class per service, clear test method naming, and shared fixtures for common setup. All tests use dependency injection for mocking rather than module-level patches, ensuring clean test isolation. Error handling tests verify that invalid inputs produce correct exception types and error codes rather than silently failing or producing incorrect results. Concurrent request scenarios are tested to verify that race conditions do not occur and data consistency is maintained. Mock call assertions verify that external dependencies are called with correct parameters and correct call counts (catching issues where services fail to call required external systems). Database state assertions verify that all expected changes occur (adoption requests created, animal status updated, donation records recorded, payment records updated). Performance baselines are established for critical service methods and remain within defined limits. Test code follows the same style and naming conventions as production code with descriptive test names explaining what is being tested and what outcome is expected.
